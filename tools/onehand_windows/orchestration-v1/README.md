# Original-source one-hand Windows orchestration v1

Source-only executable preparation. No Blender, game, Rust build, Windows job, download, GitHub mutation, publication, private asset copy, original-delta publication or native capture was performed. The current Linux work and all frozen predecessor packages are untouched. No pending vault/prone payload approval is consumed or rerouted.

## Implemented route

`run_proof.py` is a byte-pinned isolated bootstrap. `orchestrate.py` executes a sequential, fresh-candidate pipeline after all input and code-review gates pass:

1. Recheck the exact existing public r3 baseline, exact original Action delta, canonical locomotion VRA and complete 34-file Linux approved-to-replay reference using the original source package and authored bridge. Partial reference evidence cannot pass.
2. Verify the retained official Blender4.3.2 archive against its actual vendor checksum line. Probe the real safe-background Blender, build hash, loaded embedded-Python DLL and official FBX/glTF source closures. Install exact Pillow11.3.0 into embedded Python through reviewed owned processes, and retain/recheck its complete installed file inventory. No render occurs.
3. Run the original unchanged replay command through the reviewed Windows process owner. Pin actual newly serialized source and replay bytes, then invoke the existing authored-input bridge. The new BLEND has its own identity; it is never relabeled as the approved Linux BLEND.
4. Produce target-local 1/64 control export, full import and bounded import. Reverify the complete three-stage control gate. Produce the 1/256 export, independent source focus and imported focus, then verify their full gate.
5. Produce rigid-frame1/focus, geometry and all 12 bounded frame blocks. Reverify their actual stage envelopes/process evidence and conversion gate. Call the unchanged generic `assemble_stream` with the explicit full-size generated-source contract. Reuse only its existing stream/format math. Preserve all block inputs and seams. Same-candidate generated VRS/VRM bytes are copied only into the fixed private runtime layout.
6. Build the actual Windows Rust sampler with an exact reviewed Rust source snapshot and official toolchain. Run real Cargo vendor, offline metadata and offline build through owned processes. Retain actual Cargo stdout, all compiler-artifact dep-info, source/dependency before-and-after inventories, exact executable identity and generated compiler inputs linked to actual build-script OUT_DIR events. The creator calls the consumer's existing dep-info parser and final closure validators. It records the supervised whole Cargo build as producer; it does not invent inner build-script commands or logs.
7. Create a new immutable runtime context from actual assets, assembler/native references and real build output. Run actual Rust loading, fresh initialization, independent nine-time focus and all 67 chunks. For each original-grid chunk, generate source/FBX/rigid evidence first, then invoke the consumer. Reconsume the complete aggregate after all 4,240 times succeed.
8. Seal a private capture-candidate receipt with exact runtime context, sampler/build, source-lineage and asset identities. It remains explicitly unactivated. Game-side capture binding, actual native input/capture and artistic review are separate gates, not represented as complete here.

This is 222 sequential native producer stages, plus source replay/host/dependency setup and the Rust proof processes. Every native/runtime stage uses the reviewed packages' own validation and numerical bodies. No transform, quaternion, skin, geometry, interpolation or comparison implementation is duplicated in this package.

## Immutable contexts and outputs

Each stage gets an exclusive-create context under `private_root/session/candidates/candidate/contexts`. It pins only already-existing read-only input roles. Successor contexts pin actual completed predecessor output bytes and exact native/terminal/context references. Earlier contexts and receipts are never rewritten with a later hash. A repeated stage or partial output is an inspection stop, not a retry/overwrite route.

The v1 candidate-context package is used only for audited data, path and generic assembler helpers. Its blocked production transport/assembler entry is never invoked or changed. New native and runtime contexts own their distinct entry boundaries.

Exact original bounds remain: source1–96 at60Hz; 256 subdivisions; 24,321 runtime keys at15,360Hz; all148 source bones, canonical72 runtime bones, three actors, all three skins/10,234 vertices; 4,240 original ordered times in67 chunks; separate nine-time focus/four offkeys; strict matrix/position error below1e-4 and projection ray error below1e-5; 12 blocks/11 exact seams. Source/rest restoration remains enforced by the original native producer. Windows source-to-FBX-to-Rust self-parity does not claim bit-identical Linux/Windows evaluation.

Every owned process retains the unchanged 3GiB sampled direct-child RSS bound, 3GiB+512MiB initial available-memory requirement,1GiB free-disk floor and1,800-second stage deadline. Cargo descendants are owned for lifetime cleanup; the RSS claim remains direct-child sampling, not aggregate build-tree memory. The controller requires an additional8GiB initial capacity and stage-specific reserves. It performs no raw retirement; a disk failure preserves the attempt. The ordinary hosted job's360-minute limit may require an independently reviewed longer-lived runner strategy for a measured slow complete run. It is not evidence that a full run fits this budget.

## Byte-preserving publication/materialization

`DEPENDENCIES.json` inventories132 exact source/evidence dependencies (about1.54MB), including every frozen context-v1 file, unchanged native/CPU/math helpers, source producer/portable bridge and process packages. It contains hashes/paths, not private assets or a publication action.

The prepared workflow's proposed installation path is `tools/onehand_windows/orchestration-v1`; place the YAML under `.github/workflows` only through the separately authorized source publication task. Its source role mapping is explicit in `controller-layout.template.json`. `PUBLICATION_LAYOUT.json` enumerates every source-only repository destination, including the workflow, byte-preserving bootstrap, all context/producer/consumer/process files, original helper code and actual hash-only transport evidence. It adds a `tools/onehand_windows/.gitattributes` wrapper without editing any frozen dependency. `publication_inventory.py --package-pins-sha256 <independent-final-package-SHA>` verifies every local byte and emits the complete concrete SHA256/size inventory; it performs no copy, Git action or publication. The controller template is also mapped to `tools/onehand_windows/controller-layout.json`. Held payloads, original delta, final source references and live proof-inputs manifest are explicitly excluded from this WIP inventory.

Before dispatch, the owner must prepare and independently verify `tools/onehand_windows/proof-inputs.json` using schema `rust-duty-onehand-byte-materialization/v1`. Each file record has exactly `ref` (full40-digit immutable Git commit), `repository_path`, `destination` (relative to fresh materialization root), `sha256`, `bytes`, and `kind`. Every required file from each PINS closure must appear, with the expected source layout. The original-delta entry must match the separately reviewed publication path. Include all34 hash-only reference files and their replay/index/equivalence records, exact transport review/smoke records, orchestration source files/PINS, controller layout and the entire reviewed Rust source snapshot. Rust files use destination prefix `rust-source/` and their actual source commit. The controller compares the complete resulting Rust tree against those observed Git blobs; it cannot silently omit/include extra source, `.git` or `target` subtrees.

The materializer allows original source, the exact original delta, hash-only references and only the exact previously public baseline/canonical asset identities. Raw soldier geometry, new private BLEND/FBX, raw row NPZ, new VRA/VRS/VRM, GLB or media cannot be smuggled through an ordinary source entry.

`checkout_bytes.py` uses Git `cat-file` binary streams and checks object size before reading, then exact SHA/size before and after each write. The workflow first exports its own hash-pinned bootstrap through .NET binary stdout, never PowerShell text redirection. The fresh materialized tree bypasses checkout filters and CRLF conversion entirely. All role hashes and frozen package closures are then verified again before import. Package-local `.gitattributes` is additional defense only; the workflow does not rely on root attributes or assume context-v1 has byte protection.

No complete live `proof-inputs.json` is invented here: required public source commits, delta destination and completed reference identities do not exist yet. The manifest is a binding of real published inputs, not a place to fabricate their hashes.

## Official tools and output retention

Blender URL is the official `download.blender.org/release/Blender4.3/blender-4.3.2-windows-x64.zip`, archive SHA256 `933a62a770c941e316535f893629ff106ddd2aa5a956f0081ec557439073d4f6`,405,138,423bytes. The installer fetches the official vendor checksum file and requires exactly one matching line before downloading/unpacking. A missing/different/ambiguous line fails closed. The historical Scoop manifest is not used as vendor verification. This preparation did not fetch or verify that vendor line.

Rust installation uses a full reviewed version+Windows target through official rustup and `https://static.rust-lang.org`. The installed distribution manifest, actual Cargo/rustc, relevant compiler libraries and explicit MSVC/linker/SDK files are retained and hash-checked. Python requirements are pinned to NumPy2.2.6/Pillow11.3.0 from the established package registry. Native Pillow installation has its own observed process and immutable installed-source inventory; the official Blender archive remains retained separately.

The GitHub workflow has read-only contents permissions, no stored checkout credentials, no persistent cache, no private upload path, no Drive credential and no destructive cleanup. Its sole upload allowlist is the small public `summary.json`, which contains identities/counts and a hashed failure message, never raw error text, environment values, geometry, rows or native stdout/stderr. Imported consumer CLI output and diagnostics are redirected to exclusive, bounded private log files before invocation, so a consumer failure cannot print its raw exception into CI logs. Original/private inputs, native processes' exact logs, FBX/BLEND, intermediate runtime files and all raw proofs remain runner-local and may disappear on teardown. No complete forensic backup is promised. A later game-build artifact route is outside this preparation and may consume the admitted final candidate only after its separate gates.
